ESP32 Agent — what it is

A tiny on-device assistant. The chat page at / forwards your message to any OpenAI-compatible /chat/completions endpoint (OpenAI, Ollama, LM Studio, vLLM…), and the model can call back into this ESP32 to read pins, blink LEDs, scan WiFi, remember facts, fetch web pages, or restart. Replies stream live; anything starting with ⚙️ means tools ran first.

Start in 30 seconds

  1. Open Chat and ask are you online? what is your heap and wifi?
  2. Open Functions — tick only what you need (fewer tools = cheaper + faster).
  3. Read the cookbook below and steal a prompt.

What the app can do

  • Chat with tools (/) — streaming + non-streaming fallback, last turns kept as context.
  • 10 device functions — status, GPIO, ADC, blink, WiFi scan, memory save/read, restart, web fetch. Enable/disable at Functions.
  • Memory — durable facts (mem_save) survive reboots; recent chat turns persist on LittleFS and are re-injected as context.
  • Web research — web_fetch pulls an http(s) page as text so the model can summarize fresh info.
  • Setup & OTA — Setup, WiFi, Endpoint, Firmware, Status JSON.

How to ask (so tools fire)

  • Be concrete: pin numbers, counts, URLs. blink pin 2 five times beats blink a bit.
  • Name the thing: read analog pin 34 → adc_read; is pin 13 high? → gpio_read.
  • Paste full URLs with https:// for research: summarize https://example.com/specs.
  • One job per message works best; the agent can still chain up to 3 tool rounds.
  • If the reply starts ⚙️ blink, that lists the tools that ran — then comes the summary.

Web research guide

web_fetch lets the agent look things up instead of guessing: prices, docs, headlines, changelogs. It strips pages to plain text and hands ~2000 characters to the model.

  • Always include the scheme: https://site.com/page, not site.com/page.
  • Prefer stable, mostly-text pages. Heavy JS apps and login walls return little.
  • Ask for the extraction: fetch … and list the specs, fetch … and summarize in 3 bullets.
  • Compare: fetch A and B, which board has more RAM? (two fetches, one summary).

Memory vs history

  • mem_save facts persist across reboots (4KB total, 500 chars each). Inspect at /api/memory.
  • Recent chat turns auto-persist (32KB log) and are re-injected as context — no need to re-paste.
  • To forget: open Functions → Memory → Clear memory or Clear chat log (or POST {"clear_memory":true} / {"clear_log":true} to /api/memory).

Setup & upkeep

  • Setup hub → WiFi (reboots) · Endpoint (no reboot, never touches WiFi).
  • Functions — enable/disable tools (stored as a bitmask, survives reboot).
  • Firmware — upload .pio/build/esp32dev/firmware.bin, or ArduinoOTA.
  • Status — heap, uptime, model, log sizes. Watch free_heap if replies get flaky.

Limits (honest)

  • Low RAM: big pages truncate (~2000 chars from web, 1500 chars per chat message, 800 reply tokens). Why: the ESP32 has only ~225KB of free heap, shared by the page download, the encrypted connection (~35KB for HTTPS), and the chat request itself. Fetching whole pages would crash it on large sites, so it reads with a cap and hands the model the first useful 2000 characters. Bigger chunks would also mean slower replies and higher token costs, while the reply itself is capped at 800 tokens anyway — so 2000 is the sweet spot.
  • Blocking tools cap out: wifi_scan ~2s, blink ≤15s, web_fetch ≤15s — chat waits.
  • No JS rendering, no login pages, no file downloads via web_fetch.
  • Upstream errors (bad key/model, HTTP 4xx/5xx) come back as ERROR: … — check Endpoint first.
